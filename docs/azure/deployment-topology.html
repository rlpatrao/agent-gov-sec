Azure enforcement · two methods

Method 1APIM proxy — API Management edge chokepoint
API Management edge → Function llm_proxy → Azure OpenAI. The Function re-runs enforcement from the policy (input guards, tool-plan check, output redaction) and injects the deployment server-side. Sibling Function chokepoints: data_proxy and a2a_broker.
Method 2Microsoft Agent Framework — governance middleware
MAF agents on Foundry Agent Service / Container Apps run governance middleware in-process (guard, policy, capability, rogue). Authorization is in-process middleware, fail-closed per agent × tool. There is no managed policy engine on Azure.
Data FGAC — separate chokepoint
Data reads bypass the LLM path. A separate data_proxy Function runs under its own identity and applies column masking and row filters before rows reach an agent.

How to read this. The top two layers are cloud-agnostic and depend only on the Protocol seam; the bottom three are Azure-specific. The enforcement layer shows the two methods side by side — both consume the same policy registry and write the same ledger. Azure has no managed Cedar policy engine — authorization is in-process MAF middleware (Method 2) and the policy registry plus APIM edge (Method 1).

Status. In-process governance is live and is the default cloud path. The APIM proxy (Method 1) and the Container Apps jobs are reference IaC; the Function chokepoints (llm_proxy, data_proxy, a2a_broker) are built but not deployed. There is no live governance-persona deployment on Azure — the live persona deployment is AWS AgentCore in us-east-2.
